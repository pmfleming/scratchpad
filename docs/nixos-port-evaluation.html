Scratchpad NixOS Port Evaluation

Static evaluation of the Windows-first Scratchpad repository for a Linux/NixOS version while keeping both operating systems in one repo. Prepared 2026-06-08.

Conclusion

Scratchpad is a good candidate for a NixOS version without forking the product. The core editor, document model, search, settings model, session model, and most egui UI code are already platform-neutral Rust. The repository should stay single-product and single-repo, with OS-specific behavior isolated behind a small platform layer and packaging split under packaging/windows and packaging/linux.

The recommended direction is not to create a separate Linux app. Instead, keep one scratchpad crate and introduce narrow platform adapters for filesystem locations, file watching, file manager integration, command-line wording, window chrome policy, and release packaging. Windows remains the primary supported release lane while Linux/NixOS is brought up as a second validated target.

Port Feasibility High
Architecture Risk Medium
First Milestone Build + Run

What Is Already Portable

  • The app is built on eframe/egui, which gives a realistic cross-platform desktop path for Linux and NixOS.
  • The core domain code under src/app/domain appears independent of Windows APIs.
  • File loading, encoding detection, save analysis, search, session serialization, and settings serialization are ordinary Rust modules rather than shelling out to Windows tools.
  • The Windows file watcher crate already has a non-Windows fallback that compiles to a no-op worker thread.
  • Windows-specific reveal behavior is already guarded with #[cfg(target_os = "windows")], which shows the repo has started using conditional boundaries.

Main Porting Risks

Area Current State NixOS Impact Recommendation
High Build environment The repo has rust-toolchain.toml, but this NixOS shell did not have cargo available. Linux development and CI cannot be trusted until a reproducible shell exists. Add a Nix flake or dev shell that supplies Rust, native GUI libraries, pkg-config, and any rfd/GTK/Wayland/X11 dependencies.
High Data locations SessionStore::default() and SettingsStore::default() use std::env::temp_dir().join("scratchpad"). On Linux, temp directories may be cleaned. Settings and unsaved session restore should not live in temp. Create a platform data-dir adapter. Use a stable XDG location on Linux, likely $XDG_DATA_HOME/scratchpad for sessions and $XDG_CONFIG_HOME/scratchpad for settings.
Medium File watching crates/windows_file_watch uses native Windows APIs and becomes no-op on non-Windows. External file change detection will silently not work on NixOS. Rename the concept from Windows-specific to platform-specific, then implement Linux using notify or explicit polling. Keep the current Windows implementation if it is reliable.
Medium Custom window chrome src/main.rs always uses .with_decorations(false), and app chrome uses egui viewport commands for drag, resize, minimize, maximize, and close. Borderless windows and client-side resize can behave differently across Wayland, X11, Hyprland, GNOME, KDE, and NixOS packaging. Make custom chrome a platform/runtime option. Start Linux with native decorations unless the custom chrome is verified on Wayland and X11.
Medium File manager integration Menus say "Reveal In Explorer" and non-Windows returns unsupported. Linux users need "Show in Folder" behavior via portals, xdg-open, or file-manager-specific commands. Replace user-facing wording with "Show in Folder" and route through a platform adapter. Prefer opening the parent directory portably first, then add selection support where available.
Medium Dialog portals The app uses rfd::FileDialog directly. On NixOS/Wayland, file dialogs may depend on GTK or xdg-desktop-portal availability. Validate rfd on the target desktop stack. Document runtime dependencies and include them in the Nix package/dev shell.
Medium CLI conventions Help text and examples use scratchpad.exe, Windows paths, and slash switches. The Linux binary should feel native while keeping Windows compatibility. Keep parser compatibility but generate platform-specific help text: scratchpad --clean ~/notes/a.txt on Linux and existing slash examples on Windows.
Low Packaging Windows MSI packaging is isolated under packaging/windows and PowerShell scripts. NixOS packaging can be added alongside it without changing the Windows installer. Add packaging/linux or a root flake output for packages.x86_64-linux.scratchpad. Keep release artifacts separate by OS.

Recommended Repository Shape

Keep the current one-crate application, but make platform concerns explicit. A clean target shape would look like this: 

src/
  main.rs
  app/
    platform/
      mod.rs
      data_dirs.rs
      file_manager.rs
      file_watch.rs
      windowing.rs
      cli_help.rs
      windows.rs
      linux.rs
packaging/
  windows/
  linux/
    scratchpad.desktop
    scratchpad.metainfo.xml
flake.nix

The important rule is that #[cfg(target_os = "...")] should concentrate inside app/platform and packaging scripts. Core editor modules should ask for capabilities, not operating systems.

Platform Layer Boundary

The platform layer should expose small functions or services that the rest of the app can call without knowing the OS:

  • app_data_dir(), app_config_dir(), and possibly cache_dir().
  • show_in_folder(path) for Explorer, xdg-open, portals, or desktop-specific behavior.
  • FileWatchService with Windows native implementation and Linux notify/polling implementation.
  • default_window_decorations() or a persisted setting for native versus custom chrome.
  • usage_text() that emits OS-appropriate command examples.
Keep shared behavior shared. The document model, encoding rules, search, restore conflict behavior, undo history, and editor rendering should stay common unless a specific OS forces a different external integration.

NixOS Package Strategy

For NixOS, add a real Nix build path early. That gives you repeatable local builds and makes the Linux CI lane honest.

  1. Add a flake.nix with devShells.x86_64-linux.default and packages.x86_64-linux.scratchpad.
  2. Use rustPlatform.buildRustPackage or a crane/naersk setup once dependency locking is stable.
  3. Include native dependencies needed by eframe/winit/rfd on Linux, then trim after the first successful build.
  4. Install a desktop file, icon, and app metadata under the Linux packaging path.
  5. Add a GitHub Actions Linux job that runs cargo fmt --check, cargo clippy --lib --all-features -- -D warnings, and cargo test on Ubuntu. Add a Nix build job after the flake exists.

Migration Plan

Phase 1: Prove Linux Build and Runtime

  • Add the Nix dev shell and get cargo check working on NixOS.
  • Run the app with native decorations on Linux first to avoid Wayland chrome friction during bring-up.
  • Fix compile errors with the smallest possible app/platform surface.
  • Add Linux CI once local Linux builds pass.

Phase 2: Correct Linux Behavior

  • Move settings and session restore out of temp directories into XDG paths.
  • Implement Linux file watching with notify or a conservative polling fallback.
  • Change "Reveal In Explorer" to "Show in Folder" and add Linux behavior.
  • Make CLI help platform-aware while preserving Windows slash switches.

Phase 3: Package and Release

  • Add Linux desktop metadata and icon installation.
  • Add a Nix package output and, optionally, an AppImage or tarball for non-Nix Linux users.
  • Keep Windows MSI signing and release flow unchanged; add Linux artifacts as a separate release job.

Specific Code Findings

  • src/main.rs: windows_subsystem = "windows" is correctly cfg-gated, but .with_decorations(false) is unconditional. This should become platform-aware.
  • src/app/services/session_store/mod.rs: default root uses temp storage. That is not suitable for Linux session restore.
  • src/app/services/settings_store.rs: settings live beside the temp session store. Move them to a real config path before treating Linux as supported.
  • crates/windows_file_watch: the name and comments are Windows-specific, but the public API is generic enough to become the platform watcher API.
  • src/app/shortcuts.rs and src/app/ui/tab_strip/context_menu/location_actions.rs: Explorer-specific wording and unsupported non-Windows behavior should move behind a shared "show in folder" feature.
  • .github/workflows/ci.yml: CI only validates Windows. Add Linux before making NixOS changes large enough to drift.
  • packaging/windows: already isolated well. Mirror this structure for Linux rather than mixing packaging logic into app code.

What Not To Do

  • Do not create a second Linux-only copy of the app or a long-lived branch. The shared editor core is too large and valuable to duplicate.
  • Do not scatter new #[cfg(target_os = "linux")] checks through domain, search, editor, and UI modules.
  • Do not make Windows behavior depend on Linux packaging work. Keep the existing MSI path stable.
  • Do not accept a no-op Linux file watcher as final behavior if external-file-change warnings are part of the product promise.

Verification Limitation

Compile verification was not possible in this shell. Running cargo check failed because cargo is not installed in the current NixOS environment. The evaluation is therefore based on static source inspection. The first implementation step should be adding a reproducible Nix dev shell and confirming the current code either compiles or exposes the exact Linux build failures.

Final Recommendation

Proceed with a NixOS version in the same repository. Treat the port as a platform-boundary cleanup plus Linux packaging project, not as an application rewrite. The best first pull request should add a Nix development environment, introduce app/platform, move data directories behind that boundary, and add Linux CI. After that, implement Linux file watching and file-manager integration behind the same adapter.
