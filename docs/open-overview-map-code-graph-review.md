The Open Overview map is strongest as a practical architecture risk surface: it combines the dependency graph from `scripts/map.py` with maintainability, change, correctness, performance, locality, leverage, churn, test-evidence, layer, and cycle signals, then makes those signals navigable in the dashboard. Against a standard code graph analysis baseline, that is already above a plain module-dependency viewer because each node carries both structural evidence and operational context. The current generated map reports 349 nodes, 783 edges, 144 cycle members, and 141 modules without test evidence, so it is giving reviewers enough scale and risk density to decide where to inspect first.

The main gap is that the map treats the graph mostly as a decorated dependency layout rather than as a full graph-analysis object. Standard code graph analysis usually separates edge semantics, computes strongly connected components as first-class clusters, ranks nodes by centrality or instability, distinguishes public API dependencies from implementation-only references, and shows fan-in/fan-out thresholds independently from quality scores. The current map does detect cycles, dependency density, and layer violations, but those results are folded into aggregate risk numbers and detail rows instead of being exposed as graph-native views such as SCC groups, hub rankings, bridge nodes, or forbidden-direction edges.

The visual layer also trades analytical precision for dashboard readability. The main dashboard renderer lays modules out by folder or by layer and draws SVG edges between fixed rows or columns, while the older standalone viewer used Cytoscape with Dagre for a more conventional graph layout. Folder and layer layouts are useful for product monitoring because they preserve recognizable ownership boundaries, but they can hide graph topology: dense cycles, dependency bridges, and high-betweenness modules may look like ordinary cells unless the user selects them or changes the metric color. That makes the map good for triage, but weaker for proving architectural properties.

The next improvement should be to keep the current monitoring-friendly surface while adding a graph-analysis mode that makes structural claims explicit. I would add SCC rollups, fan-in/fan-out and instability rankings, edge-type labels where extraction can support them, a layer-violation-only filter, and a centrality or bridge-node view alongside the existing risk metrics. That would let Open Overview answer both dashboard questions, such as "what is risky today?", and standard graph questions, such as "which dependencies couple the system, where are cycles, and which modules would be expensive to change?" without turning the map into another long table.
