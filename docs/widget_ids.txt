Widget ID policy assessment and implementation notes

**egui sanity check**
- Local crate version: `eframe = "0.34.1"`, which uses `egui 0.34.1`.
- egui provides the building blocks for safe ids, not a single function that automatically prevents all app-level id conflicts.
- Useful egui APIs include `Ui::make_persistent_id`, `Ui::push_id`, container `id_salt` hooks, `Options::warn_on_id_clash`, and `Context::check_for_id_clash`.
- egui still expects callers to provide unique salts/scopes. The app therefore needs a project-wide id vocabulary and audit policy.

**Implemented helper vocabulary**
- `ctx_key(key)`: persistent `Context::data` and memory keys.
- `area_id(key)` / `area(key)`: overlay, popup, and `Area` roots.
- `root_id(key)` / `layer_id(order, key)`: ids that must be independent of the current `Ui`.
- `local(ui, key)`: persistent ids derived from the current `Ui` id stack.
- `scroll_id(ui, key)`: `ScrollArea` salts derived from the current `Ui`.
- `combo_box(ui, key)`: `ComboBox` construction with a scoped id.
- `child(id, key)`: ids derived from an already-scoped parent id.
- `feature_scope(ui, feature, ...)`: explicit top-level feature roots.
- `scope(ui, key, ...)`: local child `Ui` scopes.
- `interact(ui, rect, id, sense, kind)`: custom rect interactions plus debug clash tracking.
- `track(ctx, id, rect, kind)`: direct debug tracking for wrappers that must interact outside `interact`.

The old broad `global(key)` helper has been removed. Context, area, layer, and local widget ids now use separate helper names so call sites have to declare the kind of id they are creating.

**Feature roots now explicit**
- Status bar.
- Settings.
- Editor area.
- Search dialog.
- Text history dialog.
- Tab overflow.
- Horizontal tab strip.
- Vertical tab strip.

Repeated subtrees use natural discriminators such as buffer id, view id, tab position, row id, popup id, and section name.

**Strict widget checklist for new or audited UI blocks**
- Top-level UI surfaces enter `widget_ids::feature_scope(...)` before internal widgets.
- Repeated rows and controls wrap their subtree in `widget_ids::scope(...)` or derive ids from an already-scoped parent with `child(...)`.
- `ui.interact(...)` is not used directly in app code; use `widget_ids::interact(...)`.
- `Area::new`, `LayerId::new`, `ComboBox::from_id_salt`, `Ui::make_persistent_id`, and `Ui::push_id` are centralized in `widget_ids.rs`.
- `ScrollArea` call sites must set `.id_salt(...)` from `widget_ids::scroll_id(...)` or another id derived from `widget_ids`.
- `TextEdit` call sites must provide `.id(...)` / `.id_salt(...)` when focus or state can persist across frames.
- Custom painted rows and icon controls must either use native egui widgets with scoped parents or use `widget_ids::interact(...)` for their hit target.

**App-code escape hatch removal**
- Raw app-owned id APIs are intentionally centralized in `src/app/ui/widget_ids.rs`.
- A unit test audits `src/app` and fails if app code reintroduces:
  - `widget_ids::global`
  - direct `ui.interact(...)`
  - direct `.make_persistent_id(...)`
  - direct `.push_id(...)`
  - direct `egui::Area::new(...)`
  - direct `egui::LayerId::new(...)`
  - direct `ComboBox::from_id_salt(...)`
- Remaining `.id_salt(...)` usage is allowed only when the value passed in comes from `widget_ids`.

**Follow-up audit target**
- If this policy is extended further, the next useful pass is custom `allocate_exact_size(..., Sense::click...)` responses. Several are native egui allocation responses rather than raw id constructors, but interactive custom-painted widgets should continue moving toward explicit `widget_ids::interact(...)` ids when audited.
