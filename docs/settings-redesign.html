Design rationale

Proposal notes

Organize around what people are trying to change, not the implementation. Show the setting once, make its control predictable, and keep explanations only where they prevent a mistake.

01 / STRUCTURE

One list, five expandable groups

Appearance, Editors, Workspace, History and Application stay in one scrollable page. Expand several groups at once, or collapse any you do not need. No sidebar or separate settings screens.

02 / CONSISTENCY

One row, one decision

A stable label column and a right-aligned control column. Shared row height, spacing and control sizes. Font and size dropdowns share a left edge in the control column. Text and tab previews share the same font, colors, padding and preview frame. Only the five expandable categories have containers; inner groups use quiet headings and dividers, never another rounded card. No section-reset controls.

03 / LANGUAGE

Labels that do the explaining

“Editor padding”, not “Gutter”. “Memory across all files”, not “Total”. “Saved undo per file”, not “Persisted per file”. Remove sentences that merely repeat the label.

04 / DISCLOSURE

Hide complexity, not everyday settings

Text, background and highlight controls remain visible in every appearance mode. Recovery payloads have no inner disclosure. All three undo limits stay visible with sliders and exact MiB inputs. Only dependent timing remains tucked away. Search opens matching groups, then restores their previous expansion state.

Interaction contract
  • Search all groups. Match labels and older terms such as “gutter”, “persisted” and “archive”. Reveal matching collapsed content and show its category. No horizontal scrolling at narrow window sizes.
  • Apply valid changes immediately. No Save button for ordinary preferences. Commit numeric edits on Enter or blur; reject invalid values inline and keep the last valid value. Display a save failure rather than falsely claiming success. Startup choices apply on the next launch; no explanatory footer is needed.
  • Respect dependencies. System appearance keeps all controls visible. Editing an appearance control explicitly switches to Scratchpad, and editing a color selects Custom. Auto-hide remembers the delay while off. New-tab placement remains available even when files open in the current tab: users can still create tabs.
  • Reset safely. No reset buttons or reset labels within category headers. Keep only the explicit global reset in Application, with confirmation. Retention changes that can prune data need a clear consequence before applying; a lower budget is not an immediate disk-space guarantee.
  • Do not equate zero with unavailable. Load disk usage asynchronously. On failure, show Retry and an unavailable state while keeping policy controls editable. Show a neutral “No data” pie only for a successful zero result.
  • Accessible by default. Native-style keyboard behavior, named controls, visible focus, readable contrast, non-color labels, 36px controls and generous row targets. No vital help available only on hover.
Scope & implementation

Existing behavior All preference concepts above come from the current Rust settings UI. The sample values are illustrative, not a claim about shipped defaults. No additional “sync”, account or telemetry settings are invented.

New UI work Flat expandable groups, search aliases, aligned synchronized sliders, shared previews, retention presets, validation and dependency handling need implementation. Reuse existing settings-controller actions and their persistence semantics; do not write a parallel settings layer.

Prototype only Expandable groups, search, synchronized sliders, dependencies, shared text/tab preview styling and global reset work locally. Charts use example data. Open-file and recommended-limit actions are demonstrations. No files are opened, no OS settings or available memory are read, and no preferences survive a reload.

Suggested order: 1. Regroup and shorten copy → 2. Shared row/control components → 3. Precise numeric inputs and dependencies → 4. Search and validation → 5. Visual and accessibility regression tests.
