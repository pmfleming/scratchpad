A small performance lens.
A real Scratchpad process.

Establish repeatable responsiveness, CPU, GPU, memory and I/O measurements without adding instrumentation or dependencies to the editor. Keep the harness with the project, but outside its application code and build.

1. Recommended direction

Observe the release applicationLaunch a supplied binary in an isolated synthetic session. Sample OS counters and correlate them with explicit workload phases.
Keep the tool smallA Python 3.11+ standard-library CLI, Linux collectors, one optional desktop adapter, JSON/CSV data and a self-contained HTML report.
Be honest about scopeResource usage is directly observable. Visible-response timing needs a validated capture method. Missing GPU or latency support stays unavailable, never zero.

Do not rebuild the existing performance dashboard or migrate the entire sibling lens. Retain it for optional internal benchmarks and diagnosis. The new tool answers a narrower question: “Does this actual build respond promptly, and what does it consume while idle and during representative work?”

Interpret “stored with the project, external to the code” as a versioned scratchpad/tools/performance-lens/ directory, not a linked application module, Cargo target or runtime feature. Python is a deliberate choice for this new external harness; the existing sibling lens remains Rust-only.

First useful result: a roughly five-minute visible/hidden idle smoke run with CPU, RSS and I/O timelines; GPU counters when supported; map/reveal timing proxies; explicit capability and failure reporting. Automated visual-response measurements follow a feasibility gate rather than being claimed up front.

3. Storage and isolation contract

  tools/performance-lens/

      manifest.json
      samples.jsonl
      events.jsonl
      summary.json
      samples.csv
      report.html
      logs/
    fixtures/                   # ignored deterministic synthetic inputs
  • No production integration: no application imports, crate links, new in-app timers, allocator hooks, renderer patches, Cargo dependencies or packaging changes. Deleting this directory must not change the application build or behavior.
  • Binary first: require --binary pointing to a prebuilt executable. Build separately, outside measured intervals. Record resolved path and SHA-256; never assume an installed Nix binary matches the current checkout.
  • Own test state: fresh private XDG_CONFIG_HOME, XDG_STATE_HOME, XDG_CACHE_HOME and TMPDIR. Verify broker isolation and that the owned PID maps a window; forwarding to another instance invalidates the run. Retain the normal display connection and XDG_RUNTIME_DIR rather than blindly replacing it.
  • Own processes only: track PID plus Linux start time, executable and owned process group. Window operations must resolve that process identity, not match every window named Scratchpad. Graceful close, then bounded termination of owned processes only; never pkill scratchpad.
  • Desktop consent: native scenarios are opt-in and may steal focus. Restore prior focus/workspace where safe; do not edit compositor rules or the normal user session. Abort on unexpected focus before synthetic input.
  • Local privacy: synthetic documents only by default. Keep captures/protocol logs local and opt-in; omit document text, window titles and arbitrary environment dumps from normal artifacts.

The existing docs/measurement-tools.md describes sibling ownership. At implementation time, add a small documented exception for this self-contained external harness; do not relocate or remove existing probes, benches, configs or sibling-lens contracts.

4. Minimal metric contract

Default sampling: 250 ms for lightweight process counters; 1 second for GPU and optional heavier memory detail. Use actual monotonic elapsed time, not the requested sleep duration. Save timestamps, phase, raw counters, derived values, source, units, scope and availability reason.

AreaMeasurement / sourceReport and caveat
CPU/proc/PID/stat: user + system ticks. 100 × Δticks / CLK_TCK / Δseconds.CPU seconds, phase-average CPU and sampled peak; 100% means one logical core, so multithreaded values may exceed 100%. Report tick resolution; “0 observed ticks” does not mean zero work.
Memory/proc/PID/status: VmRSS, VmHWM, threads. Optional smaps_rollup: PSS/private memory at lower frequency.Start/end RSS, sampled peak RSS, post-work retained RSS and repeated-cycle growth. VmHWM is lifetime high-water, not a resettable phase peak. No claim to observe allocator traffic or every transient allocation.
I/O/proc/PID/io: read_bytes, write_bytes, rchar, wchar; stat: minor/major faults.Phase byte deltas and sampled rates. Storage-accounted bytes and syscall character counts stay separate. Cached/mapped reads can show little read_bytes; writes may be buffered, not durable. A sampler cannot measure per-request storage latency.
GPU enginesDiscover DRM descriptors through /proc/PID/fdinfo/*. Read supported drm-engine-* counters and capacity metadata.Per-device, per-engine busy-time deltas; derive percentage only when units/capacity semantics are known. Deduplicate by device + DRM client ID, including duplicate descriptors. No invented universal “GPU %” by summing unlike engines.
GPU memorySupported DRM client memory/resident/shared fields, preserving their driver-defined names and meanings.Report per-region attributed bytes where available. VRAM/GTT/shared system memory are not interchangeable; do not add GPU memory to RSS as a total. Integrated-GPU memory may overlap system memory.
Host contextCPU/GPU model, kernel, driver, compositor, output size/scale/Hz, renderer request and observed backend when available, power mode and host load.Identify confounders and comparison mismatches. Optional whole-device GPU busy counters must be labelled “system-wide”; compositor/other-client work is not app work.
Tool overheadHarness CPU time/RSS, collection durations, late samples and capture mode.Show monitoring cost separately. Sampling spikes and missing intervals must not silently become application spikes or interpolated zeroes.

Process scope: MVP primary-process counters include its threads, not the launcher, compositor or unrelated Scratchpad instances. List detected owned child processes; if child collection is added, retain per-process rows and explicitly label any aggregate. Do not imply sum-of-RSS is unique physical memory.

Counter lifecycle: first sample has no delta. Process exit, PID reuse, lost permissions, counter decrease, GPU client reset or missing fields produce null plus a reason. Rediscover GPU clients periodically because the renderer can open them after startup. No negative rates, stale last-value continuation or missing-to-zero coercion.

The GPU feasibility check is an early deliverable. On a driver without usable per-process counters, the report must say “app GPU utilization unavailable.” Optional vendor tooling is a later adapter—not a reason to require root or delay the basic CPU/memory/I/O lens.

5. Responsiveness without app instrumentation

Separate three evidence levels. Low CPU does not imply responsiveness: the application can be blocked while consuming nothing.

LevelExternal observationAllowed claim
Basic lifecycle proxiesTimestamp process launch, first PID-owned mapped window, reveal request and successful window close. Polling interval and command round-trip time are recorded.Launch-to-window-mapped and close completion, not launch-to-usable, rendered content or editing latency. Hidden tests explicitly verify resumption on reveal.
Visual response — capability-gatedA desktop adapter injects a unique deterministic edit/search/tab action and captures a narrowly defined editor/result region. Detect the expected content change, not any pixel change or caret blink. Timestamp submission and capture observation with a common monotonic clock.Input-command-to-observed-visible-change, including injection and capture overhead. Not exact physical input-to-photon or an internal event-loop timer.
Optional diagnosticsSeparate runs using existing window tracing/Wayland protocol logging or existing sibling-lens probes.Ping/pong dispatch and tessellation timings remain diagnostics with separate scopes. They do not replace visible response or certify GPU presentation.

Visual measurement feasibility gate

  1. Use a compositor-supported capture path and an explicitly permitted input mechanism. Detect the installed Hyprland command API; the local native script uses Lua dispatch and must not be assumed portable to every version.
  2. Check that capture timestamps have known semantics. At a 60 Hz capture cadence the nominal observation granularity is about 16.7 ms, before capture pipeline delay. Report cadence, dropped captures and measured method overhead.
  3. Retain the last unchanged and first changed observation timestamps. Treat response as an observation interval, with capture uncertainty, rather than false sub-millisecond precision. Validate action success using expected fixture content, a verified saved result where applicable, or an explicit visual assertion.
  4. Test against a controlled external test window with known delayed updates. Verify that no-change, unrelated repaint, lost focus and timeout cases cannot pass. If the method is unreliable, ship resource measurements with latency unavailable and a reproducible manual observation protocol—not fabricated percentile timings.

Initial interactive metrics: edit-to-visible-character, search-command-to-visible-result, tab-switch-to-expected-content, and reveal-to-visible-editor. Scrolling gets resource traces and visual completion checks first. Displayed frame pacing/jank stays deferred until actual presentation timestamps or a validated frame-capture method exist; 250 ms resource polling cannot measure frames.

6. A deliberately small scenario set

Generate fixtures before measurement with a fixed seed and content hash. Keep line lengths, encoding, match count, file size and settings in the manifest. Start modestly; a 1 GiB file or 10,000 tabs is an explicit stress extension, not the default smoke test.

Each renderer profile gets separate baselines. Native app-ID/workspace behavior remains part of the scenario; do not “fix” measurement conditions by removing the rule that triggered past failures.

7. Baselines, statistics and artifacts

Run discipline

  • Run serially on the same machine with consistent power mode, display, renderer, settings and workload. Avoid builds and unrelated GPU-heavy tasks. Record rather than silently change the CPU governor, compositor configuration or user environment.
  • Use at least three independent process launches per baseline resource scenario. For version comparisons alternate A/B ordering and retain all runs. Report individual run values, median and range; do not claim statistical significance from three runs.
  • For response trials report sample count, median, maximum, timeout count and raw chronological observations. At 30 trials, p95 is only a rough descriptive order statistic; show it as low confidence, suppress p99 until at least 100 trials, and still label p99 descriptive rather than a tail guarantee. Never pool phases or metric scopes.
  • Retain failed actions and timeouts as failures with a censoring limit. Successful-trial percentiles must not conceal them. Resource samples are a time series, not independent user-response trials.
  • No global cache dropping, root privileges, unconditional protocol logging, renderer overlays or always-on screenshot capture in normal resource runs. Separate low-overhead resource runs from capture-heavy responsiveness/diagnostic runs.

Comparison policy

First establish a baseline; do not invent universal pass budgets from old internal-probe results. Store human-approved scenario budgets later in scenarios.toml. A comparison uses matching workload hashes, metric definition/schema, backend, display settings and machine profile. Otherwise report incomparable with reasons.

A provisional regression alert requires both an absolute change floor (above quantization/noise) and a relative change threshold, confirmed across repeated runs. Near-zero baselines use absolute differences only. The report separates measurement complete / partial / failed from within budget / above budget / uncertain / no budget. Timeouts remain failures even if a successful-trial median is fast.

Reproducible run manifest

Record schema version, UUID, UTC time plus monotonic origin, harness revision/hash, app executable hash, optional source revision/dirty fingerprint, build provenance when known, command arguments, allowlisted settings/environment, host/driver/display metadata, PID/start time, fixture hashes, scenario revision, collector capabilities, sampling intervals and exit/timeout status. A checkout revision alone does not prove binary provenance.

Each sample carries actual interval and metric availability. Each event carries phase/action ID, timestamp, start/stop definition and outcome. Preserve raw evidence and failed-run diagnostics; write final artifacts atomically. Capture permission failures and unsupported counters remain distinct from a measured zero.

One useful HTML report

Top row: scenario, build identity, run status and capability gaps. Then five sections—responsiveness, CPU, GPU, memory and I/O—with phase-aligned timelines, summary tables, baseline deltas and failure counts. Generate inline SVG and tables from local data; no network assets, server or CDN. Embed data or render it at generation time so opening report.html via file:// works. Escape all untrusted labels/log text.

Keep historical baselines for comparison instead of automatically expiring them after 24 hours; label their age and context. They are historical evidence, not certification of the current executable. Set an explicit local run-retention budget; never silently prune a selected baseline.

9. Acceptance checklist

  • Separation: app source, Cargo manifests/lockfiles and production packaging remain unchanged. The basic lens runs against a supplied release binary with no sibling repository or internal probe build.
  • Safety: tests cover an already-running user instance, failed broker isolation, missing window, lost focus, process crash, hung child, Ctrl-C and PID reuse. Cleanup cannot target an unrelated process or touch normal settings/session files.
  • Correct collectors: fixtures cover process names containing spaces/parentheses, tick/page units, missing proc fields, permission denial, counter resets, duplicate DRM descriptors, engine capacity and disappearing GPU clients. Cross-check CPU and RSS against a known workload/tool; allow expected quantization differences.
  • Honest responsiveness: map time is not labelled ready time; visual latency includes its method and uncertainty. Known delayed updates are detected, no-change actions time out, and unrelated repaint cannot count as success.
  • Useful baselines: at least three independent visible/hidden resource runs and, where supported, 30 verified actions per interactive type. All failures survive aggregation. Renderer/host/workload mismatches prevent automatic pass/regression judgments.
  • Low overhead: measure sampler self-cost and compare low-rate versus default-rate runs. Initial engineering target: under 1% of one core for the sampler in settled resource runs; this is a target to verify, not a present claim. If overhead or sampling delays are material, lower cadence and show the limitation.
  • Bounded execution: scenario timeouts, fixture-size caps, disk budget checks and graceful interruption. Optional cgroup resource limits only when available, with their values recorded; do not claim a sampled RSS alarm prevents OOM.
  • Portable report: open HTML offline; missing GPU/latency data is readable; labels are escaped; corrupted/truncated artifacts fail validation; selected baselines are preserved.
Definition of done: one command measures an isolated real Scratchpad build, produces a trustworthy local report covering resources and supported responsiveness observations, and leaves the editor code and the user’s working session alone.
